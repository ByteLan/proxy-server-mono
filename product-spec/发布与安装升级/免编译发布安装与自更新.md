# 免编译发布安装与自更新

## 1. 业务规则（当前生效）

- **开发机手动构建发布、服务端零编译**：仓库不配置任何 GitHub Actions 自动构建或自动发布工作流；单纯 `git push` 或打 tag 不会生成可下载二进制。维护者在开发机干净且已推送远端的 Git 工作树上执行 `make publish`（`scripts/publish-release.sh`），本地交叉编译 3 种 Linux 架构（`amd64`、`arm64`、`armv7`）共 6 个静态二进制（管理端已内嵌最新 `internal/webui/dist`），连同 `install.sh`、`install-bundle.tar.gz` 与 `SHA256SUMS` 共 9 项资产通过 `gh` 上传发布。
- **双发布渠道**：默认发布 `main-<12位commit SHA>` prerelease（对应服务端默认 `main` 渠道）；传入 `--tag vX.Y.Z` 发布正式 release（对应服务端 `--channel stable`）。已发布 tag 资产不可变，未完成草稿支持重跑恢复。
- **Bootstrap 安全校验安装**：服务端通过 `scripts/install.sh`（可从仓库副本或 GitHub API 获取）下载目标架构二进制、`install-bundle.tar.gz` 与 `SHA256SUMS`，离线核验 SHA-256、ELF 架构头及 tar 包白名单（仅允许固定 4 个安装脚本/systemd 单元普通文件，拒绝软硬链接与路径穿越）后完成初始化。重复执行安装脚本保留已有的 `manager.env`、SQLite、`node.env` 与 `config.json`。
- **内置原子自更新与 `.previous` 回退**：`proxy-manage-server update` 与 `proxy-server update` 仅下载并核验对应服务可执行文件，同目录原子替换并将旧版保存为 `<binary>.previous`（更新管理端二进制即一次性完成前后端升级）。`update` 不修改配置、SQLite 或协议核心，且**不自动重启服务**，由管理员显式执行 `systemctl restart`。
- **三权分离的 GitHub 凭据**：开发机发布使用具备仓库 `Contents: Read and write` 的凭据；私有仓库 VPS 下载仅使用单仓库 `Contents: Read-only` 的 Fine-grained PAT（通过 `--token-file` `0600` 文件或临时环境变量传入），跨域重定向下载存储资产时自动剥离 `Authorization` 请求头。

## 2. 跨端代码锚点

- **多架构打包与发布脚本**：`Makefile`、`scripts/build-release.sh`、`scripts/publish-release.sh`
- **服务端 Bootstrap 与组件安装器**：`scripts/install.sh`、`scripts/install-proxy-manage-server.sh`、`scripts/install-proxy-server.sh`
- **自更新核心逻辑与 CLI 封装**：`internal/selfupdate/update.go`、`internal/updatecmd/run.go`
- **发布与安装离线回归测试**：`scripts/test_publish_release.py`、`scripts/test_install_bootstrap.py`

## 3. 模块红线

- 严禁将 `/opt/proxy-manage-server/bin` 或 `/opt/proxy-server/bin` 改为服务运行用户可写；服务进程严禁后台静默自升级。
- 严禁将 GitHub PAT 写入命令行明文参数、公开日志或长期驻留的 systemd `EnvironmentFile`。
- `.previous` 仅回退可执行二进制，**不会回滚已执行的 SQLite 数据结构迁移**；管理端大版本升级前必须先停服完整备份 `DATA_DIR`（含 `manager.db` 与 `master.key`）。
